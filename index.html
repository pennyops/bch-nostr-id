BCH ⇄ Nostr identity verifier

Checks whether a Nostr key has published a signed binding to a Bitcoin Cash address (kind 30078, d=bch-nostr-bind). Both signatures are verified in your browser: the Nostr schnorr sig and the BCH signmessage sig. Nothing is sent anywhere except relay queries. Wallet devs: see the draft spec (npub to BCH address, for Cashonize #405).

Prove you are the payer (stretch: proof-of-payment login)


A merchant can link a session to a payment without any account: the payer signs a fresh challenge with the BCH key of an address that funded the transaction (Electron Cash: Tools > Sign/verify message). Transaction inputs are fetched from the public Blockchair API. The challenge commits to the txid, this site, a random nonce and a timestamp, so a signature cannot be replayed for another order. Caveat: this proves control of an input key (the payer of record). For exchange withdrawals or pooled/CoinJoin txs that is not the customer, so it is strongest for self-custody payers.

How it works


A binding is one Nostr event (kind 30078, d-tag bch-nostr-bind). Its content is the statement bch-nostr-bind.v1:<nostr pubkey hex>:<cashaddr>:<unix ts>. It carries the tag ["i","bch:<cashaddr>","<base64 BCH signmessage sig>"].


To verify: (1) check the event id and the BIP-340 signature; (2) check that the statement names this pubkey and the address in the i-tag; (3) recover the public key from the BCH message signature and check that it hashes to that address (q... or token-aware z...). Both keys sign the same statement, so neither side can claim the other alone. Rebinding = publish a newer event (addressable kind, latest wins).


Python: binding.verify_binding(event) returns (ok, address, reason); discover.py lookup <hex> queries relays. auth.py has a challenge-response login (a site sends a nonce, the user signs it with the bound BCH key).


NIP-39 profile claim (optional): the same i-tag can be copied into your kind 0 profile tags, so clients that render external identities show the address. Your profile then points at it; the kind 30078 event stays the full verifiable record (the i-tag proof is the BCH signature over the statement, which clients rebuild from the binding event). Example: the npub behind this page lists bch:bitcoincash:qqheja48x3q3u8vxv5eue74gzpcf6x49cs5zxa36g7 this way.
